ACT 1

需求变成规格

主会话（orchestrator）先读需求原文，把模糊的地方逐条问用户（这里由模拟用户按推荐项回答），再整理成带编号的需求（REQ）和验收标准（AC）。AC 是 Given / When / Then 写法的、用户能感知的行为，后面每一条都要有人认领、有测试覆盖。虚线框的 AC 是只能人工确认的界面项。

ACT 2

架构师拆任务

硬依赖：必须等对方合入软依赖：可以对着契约先写点卡片看详情 · 悬停看依赖

每条 AC 归谁

每格是一条 AC，颜色是负责它的任务；架构师必须让每条 MVP AC 恰好归一个任务，程序会检查。

可写范围地图（writes）

架构师给每个任务划定要改的文件。程序用它决定谁能和谁同时干：范围重叠的任务不同时运行。红色的是后来出事的那个文件。

ACT 3

并行施工

每一条色带是一次 agent 运行（一个独立子进程）。按「播放」把整次运行压缩成几十秒回放：右边滚动的是程序记下的事件，上方的圆点是此刻同时在干活的 agent 数。点色带看这次运行的模型、轮数、token 和花费。

ACT 4

每人交了什么

每个任务在自己的 git worktree 里干活，交付物是一组提交和一份 handoff（交接笔记：做到哪、下一步、注意什么）。已合入的看集成分支上的提交，没合入的看它的任务分支。绿色是代码，蓝色是测试。

当时的规则
worker 只能改计划里分给它的文件（writes）。要改别的文件得申请；如果那个文件属于一个正在运行的任务，申请直接被拒，连主会话也不能批准。

      
改了之后（偏离 115）
worker 不再受 writes 限制：除了验收测试和规格，什么文件都能改，在交接笔记里写明即可。writes 只用来安排谁和谁可以同时干；真的同时改了同一个文件，合并时程序会生成一个专门解冲突的任务。
