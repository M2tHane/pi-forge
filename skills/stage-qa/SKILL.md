# 阶段验收

程序已经做完了：全量测试、验收测试、契约检查，以及 AC 覆盖率矩阵。你的价值在于**通读多个模块**之后才能看到的问题。
一个阶段内的每个 task 都单独通过了验收，但合在一起，用户可能仍然用不起来。

## 1. 覆盖是否名副其实（抽查）

从覆盖率矩阵中挑出风险最高的 AC 抽查（涉及权限、金额、删除、并发的优先），每条读对应的测试：

- 断言是否覆盖了 AC 的 Then（只检查 200 不算）。
- 是否测到了 AC 说的情况（例如 AC 说"同团队重名"，测试却建了两个不同团队的数据源）。
- 发现形同虚设的测试，作为 must 提出，basis 写 `ac:<编号>`，files 写测试文件。
- 页面 AC 的验收测试只测脱离浏览器能验证的部分（页面路径、接口、前端纯逻辑），这是约定，不算形同虚设；页面本身由你在第 4 步用浏览器检查。

## 2. 跨模块一致性

| 查什么 | 依据 |
|---|---|
| 同一个概念在不同模块里的命名 | glossary.md |
| 错误响应的结构、错误码的使用 | openapi.yaml 的 Error、errors/*.yaml |
| 分页、排序、时间、金额的格式 | openapi.yaml 的 components、rules/ |
| 同一个功能有没有两套实现（两个模块各写了一个权限检查） | arch/overview.md 的分层 |

用 grep 和 codegraph 查，不要逐个文件通读。

## 3. 权限抽查（实际运行）

- 用 forge_service 启动服务（commands.serve；端口和数据库由程序分配，见环境变量 PORT、FORGE_DB_NAME），用完停止。
- 对本阶段涉及的资源，按 permissions.md 逐个角色试：允许的操作成功，拒绝的操作返回 FORBIDDEN，跨团队访问返回 NOT_FOUND 或 FORBIDDEN（以契约为准）。
- 每次请求与响应都记作证据。

## 4. 页面能用、状态齐全

用技能 playwright-browser 在无界面浏览器里打开本阶段改到的页面：打不开、控制台报错、不该出现的错误提示一直显示，都作为 must（basis 写 `defect:`，附上报错原文或截图路径）。
screens.md 列出的加载、空、错误、无权限状态，能造出来的实际看一下，造不出来的在前端代码中找对应的分支或组件。找不到的作为 must，basis 写 `spec:screens.md#<页面>`。只能靠人眼判断的视觉效果写进 manual。

## 5. exit 是否达成

对本阶段 exit 中的每条 REQ，从用户角度走一遍：用到的接口都存在，并且彼此衔接（创建后能在列表里查到，删除后详情返回 404）。
用 curl 串起一条完整路径验证。

## 写报告

- must：有出处（`ac:`、`spec:`、`contract:`、`rule:`、`defect:`）、有证据、有具体的 files。
- suggest：其他改进意见，不阻塞。
- manual：需要用户打开应用确认的。
- 同类问题合并成一条。宁缺毋滥：没有问题就提交空列表。
