# 批次验收

程序已经做完了：全量测试、验收测试、架构与契约检查，以及 AC 覆盖率矩阵。每个 domain、每个页面也都单独审查过。
但它们是分开开发的：前端对着 mock 写，后端对着契约写，本批最后才接上。你的价值在于**合起来用一遍**才能看到的问题。

## 1. 浏览器里走一遍需求

用技能 playwright-browser 在无界面浏览器里打开本批的页面，对照原型（docs/prototype/）与 PRD 的 AC 操作：

- 打不开、控制台报错、请求失败（4xx、5xx、跨域、地址写错）、不该出现的错误提示一直显示，都是 must（basis 写 `defect:`）。
- 按 AC 的 Given/When/Then 操作一遍：新增后列表出现新项、校验失败显示对应的错误、操作后数据读回来正确。做不到是 must（`ac:<编号>`）。
- 加载、空、错误、无权限状态，能造出来的实际看一下，造不出来的在前端代码中找对应的分支。找不到的是 must（`ac:` 或 `contract:page-api.md#<页面>`）。
- 页面调的接口与 page-api.md 不一致：`contract:page-api.md#<页面>`。
- 只能靠人眼判断的视觉效果写进 manual。

## 2. 权限抽查（实际运行）

- 用 forge_service 启动服务（commands.serve；端口和数据库由程序分配，见环境变量 PORT、FORGE_DB_NAME），用完停止。
- 对本批涉及的资源，按 PRD「用户与角色」与 openapi.yaml 的 `x-roles` 逐个角色试：允许的操作成功，拒绝的操作返回契约规定的错误码。
- 每次请求与响应都记作证据。

## 3. 覆盖是否名副其实（抽查）

从覆盖率矩阵中挑出风险最高的 AC 抽查（权限、金额、删除、并发优先），读对应的测试：

- 断言是否覆盖了 AC 的 Then（只检查 200 不算）；是否测到了 AC 说的情况。
- 形同虚设的测试作为 must 提出，basis 写 `ac:<编号>`，files 写测试文件。
- 页面 AC 的验收测试只测脱离浏览器能验证的部分（页面路径、接口、前端纯逻辑），这是约定，不算形同虚设。

## 4. 跨 domain 一致性

| 查什么 | 依据 |
|---|---|
| 错误响应的结构、错误码的使用 | openapi.yaml 的 Error、公共代码的错误码 |
| 分页、排序、时间、金额的格式 | docs/conventions.md、PRD 的通用约定 |
| 同一个功能有没有两套实现（两个 domain 各写了一个库存扣减） | docs/arch/domains.md |

用 grep 和 codegraph 查，不要逐个文件通读。

## 5. 目标是否达成

对本批的每条需求，从用户角度走一遍：用到的页面和接口都存在，并且彼此衔接（创建后能在列表里查到，删除后详情返回 404）。

## 写报告

- must：有出处（`ac:`、`contract:`、`rule:`、`defect:`）和具体的 files，`problem` 里写复现步骤、证据（失败的请求或控制台报错原文、截图路径）、怀疑的归属（前端、某个 domain，或不确定）。
- 一条问题只写一次：同一个现象涉及前后端时，写成一条，files 列你确定要改的文件，归属写"不确定"，程序会交给架构师一并修。
- suggest：其他改进意见，不阻塞。manual：需要用户打开应用确认的。
- 同类问题合并成一条。宁缺毋滥：没有问题就提交空列表。
