# 写验收测试

本技能由实现者（后端、前端开发者，S0 则是 architect）使用：任务说明有『验收测试（由你编写）』一节，照本技能自己写 tests/acceptance/<T>/。reviewer 用同一份标准审查这些测试：每条 AC 有没有测试（程序已扫描编号）、是否真的走了 Given/When/Then 并且只经公开入口、断言有没有被弱化、有没有依赖实现细节。缺失或形同虚设是阻塞问题。

测试和实现出自同一个人，最容易犯的错是**照着实现写断言**：期望值只能来自 PRD 与契约，不能来自实现的当前输出。

验收测试决定一个 task 能不能合并。它有两种失败方式，都要避免：

- **太松**：错误的实现也能通过（只检查状态码、断言过宽、什么都没测）。
- **太紧**：正确的实现也通不过（断言了 PRD 没规定的东西、依赖实现细节、测试之间互相依赖）。
  这是实测中返工的最大来源：测试写错了，没有办法自动发现。所以本技能大部分规则是防"太紧"的。

## 测试从哪里来

对每条 AC：

1. 把 Given 变成测试准备：通过接口创建需要的数据（团队、用户、数据源），不直接写数据库。
2. 把 When 变成一次调用：本 task 对外的 HTTP 接口、页面（见下面『页面测试』）或跨模块函数。
3. 把 Then 变成断言：状态码与错误码来自 openapi.yaml；字段来自 schema。

测试名以 AC 编号开头：`[REQ-012.AC2] 同名数据源返回 409`。
**优先写覆盖多条 AC 的集成场景**：一个场景走完一条用户路径，测试名带上它覆盖的全部 AC 编号（`[REQ-012.AC1][REQ-012.AC2] 创建后同名再建返回 409`），不要求每条 AC 单独一个测试；每条 AC 至少出现在一个测试名里。

**只测关键业务节点**：在公开边界验证行为。每条 AC 至少出现在一个测试名里，但不为每个边界情况各写一个；
优先主路径、权限、数据完整性、契约规定的错误码。测试越多，写错的机会越多，也越容易卡住正确的实现。

**入口要在合入时可用**：When 的执行和 Then 的观察只用本任务实现的接口和之前已合入的接口（任务说明有『已交付的接口』一节时以它为准），不调用后续批次或同批别的 domain 还没写完的接口。Given 的数据准备优先用这些接口；需要的接口还没交付时，可以用测试夹具直接写存储。需要后续接口才能观察的场景，不自己想办法，写进 handoff。

## 只断言 PRD 与契约规定的东西

| 应该断言 | 不要断言 |
|---|---|
| 状态码、错误码 | 错误信息的文字（除非 PRD 规定了） |
| AC 关心的字段及其值 | 整个响应的精确相等（契约追加字段就会失败） |
| 清单里有本 task 交付的项；"只含已交付的"用"清单里每一项都能打开"验证 | 菜单、页面清单、路由表的完整列表（后续 task 每加一项都要改这条测试，并行时必然冲突） |
| PRD 规定的排序、分页 | PRD 没规定的顺序（用集合比较） |
| 字段类型与格式（uuid、时间格式） | 自动生成的具体 id、时间戳的值 |
| 副作用：通过另一个接口读回来验证 | 直接查数据库 |

PRD 没说清的地方：**不要猜着断言**。在 handoff 里列出来，这是 PRD 需要补充的信号。

## 页面测试

- 验收测试不开浏览器，也不为测页面引入浏览器或 DOM 模拟。页面 AC 只测脱离浏览器能验证的部分：页面路径返回 HTML、页面用到的接口（数据、错误码、权限）、前端模块里的纯逻辑（格式化、校验、按数据决定显示哪种状态）。
- 打开页面看交互和状态（新增后列表出现新项、空状态的提示、无权限时按钮不存在）由 stage-qa 在无界面浏览器里检查；视觉效果、布局、动画交给 manual_checks。
  （stock 实验：开发者为测页面状态自己搭浏览器脚本，调试占了一次运行的大半时间，脚本还写死了本机路径。）

## 独立与可重复

- 每个测试自己准备数据，用唯一的名字（加随机后缀），不依赖其他测试的执行顺序或残留数据。
- 公共的准备工作先用 tests/acceptance/_support/ 里已有的工具；需要新的辅助函数时，只能放在 tests/acceptance/_support/<本 task>/ 下，不改公共文件和别的 task 的目录。值得共享的写进 handoff，由 stage-qa 提出合并建议。
- 服务地址、端口、数据库都从环境变量取（PORT、FORGE_DB_NAME 等，S0 的公共工具已经封装），不要写死。
- 不 sleep 固定时长；需要等待时，轮询直到满足条件，并设置超时。

## 提交前

- 运行 `acceptance -- <本 task>`，确认全部通过；通过不证明断言正确，再对照下面的检查项看一遍。
- 新增或修改断言辅助函数时，用固定的正反例样本自检（不依赖实现）：符合契约的样本应通过，违反检查目标的样本应失败。
- 诊断标签与期望值用不同的具名参数（如 `{ label, expectedMessage }`）。PRD 没规定文案就不传 expectedMessage，不把标签当作期望值。
- 在执行 When 之前确认 Given 已成立：准备数据的请求也要检查结果（用户确实在项目里、角色确实建立）。
- 数据库行等带特殊原型的对象，按契约字段投影后比较值；对象原型不是业务条件。
- 返工时对照本轮全部失败和同一辅助函数的所有调用点，一次改完；修正夹具、参数误用、比较方式不算放宽。
- 对照 AC 列表，确认每条都有测试。
- 读一遍断言：一个正确但写法不同的实现，能通过吗？一个漏掉 AC 的实现，会失败吗？
