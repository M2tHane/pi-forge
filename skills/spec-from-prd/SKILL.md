# 从 PRD 与原型到规格

规格是之后所有工作的唯一依据：architect 照它写契约，test-author 只看它和契约写验收测试，worker 照它实现，stage-qa 照它验收。
test-author 和 worker 是**分别**读规格的，所以规格每一处含糊，都会变成两人理解不一致，最后变成一次测试争议。写清楚比写得长重要。

## 第一步：找缺口（在提问之前）

通读 PRD 与原型，逐项列出（用户没有提供文档时，把这份清单当作访谈提纲，逐项问到）：

1. **没有验收标准的需求**：只描述了功能，没说怎样算做到。
2. **边界行为**：重名、空值、超长、并发修改、删除被引用的数据、分页的最后一页、权限不足、资源不存在。
3. **原型缺的状态**：每个页面的加载、空、错误、无权限，内容溢出时怎么显示（长文本、很多行）。
4. **权限**：每种角色对每种资源能做什么；"自己的"与"团队的"有什么区别。
5. **术语**：同一个概念有几种叫法（数据源 / 连接 / 库），同一个词指两件事。
6. **矛盾**：PRD 与原型不一致的地方，PRD 前后不一致的地方。
7. **范围**：哪些属于这次的 MVP，哪些以后做，哪些不做。

能从输入里查到的自己查。剩下的按技能 grilling 逐轮问用户，每题给出推荐答案。先问影响范围最大的（谁用、核心场景、MVP 边界），细节放后面。

## 第二步：写四份文件

### requirements.md

```md
# 需求

## 背景与目标
一两段：为谁解决什么问题。

## 需求清单

### REQ-012 团队负责人可以创建数据源 [MVP]
角色：管理员、团队负责人
- AC1：Given 已登录的团队负责人 When 提交合法的 MySQL 配置 Then 创建成功，返回数据源 id，状态为 untested
- AC2：Given 本团队已有同名数据源 When 再次创建 Then 失败，错误码 DATASOURCE_NAME_TAKEN
- AC3：Given 员工 When 创建数据源 Then 失败，错误码 FORBIDDEN
- AC4（manual）：在列表页新增后，新项出现在第一行

## 通用约定
- 所有文本字段首尾空白裁剪；邮箱按小写保存与比较
- 校验失败统一返回 400 与 VALIDATION_ERROR

## 关键决策
- 数据源名称在团队内唯一（默认）
## 范围外
- 跨数据源联查
```

- 编号 REQ-001 起连续，优先级是 `[MVP]`、`[LATER]`、`[NO]`。
- 每条 AC 是 Given / When / Then，写成**能用接口或页面操作验证**的形式；需要人眼判断的标 `（manual）`。
- **AC 只写用户（或 API 调用方）能感知的业务行为**：一个操作在某前提下的结果。统一的输入校验、规范化、错误结构、通用状态码规则等横切细则（邮箱大小写、空白裁剪、日期真伪、标签去重、错误响应格式……）**不写成 AC**，写进 requirements.md 的 `## 通用约定` 一节（或交给契约的 errors），由一两个验收场景整体覆盖。
  - 正例：`Given 已注册邮箱 When 再次用该邮箱注册 Then 失败，错误码 EMAIL_TAKEN`。
  - 反例：`Given 邮箱含大写 When 注册 Then 按小写保存`——这是规范化规则，归入「通用约定」：`- 邮箱统一按小写保存与比较；所有文本字段首尾空白裁剪`。
  - 一条 REQ 的 AC 一般不超过 6 条；超过时先检查是不是把通用规则写成了 AC（spec-lint 会给警告）。
- AC 写行为，不写实现：写"失败，错误码 X"，接口路径与状态码交给 architect 的契约（用户特别在意的可以写）。
- 默认处理的地方在"关键决策"里标"默认"。
- 不写"快速""友好""合理"这类无法测试的词，写成具体的数字或行为。

### screens.md

每个原型页面一节：

```md
## 数据源列表 /datasources
REQ：REQ-010、REQ-012、REQ-013
字段：名称、类型、状态、创建人、创建时间
交互：新增（弹窗）→ 列表第一行出现新项；删除（确认）→ 行消失；点名称 → 详情页
状态：
| 状态 | 表现 |
| 加载 | 表格骨架屏 |
| 空 | "还没有数据源" + 新增按钮（员工看不到按钮） |
| 错误 | 顶部错误条 + 重试 |
| 无权限 | N/A：所有角色都能看本团队的列表 |
| 溢出 | 名称超过 40 字截断并悬停显示；超过 20 行分页 |
```

### permissions.md

一张表，行是"资源 · 操作"，列是角色，单元格写 ✓、✗ 或条件（"仅本团队"）。角色名必须在 glossary 里。

### glossary.md

按技能 domain-modeling 的格式：每个概念一个名字，"不要叫"列出被淘汰的叫法，中文名后附代码里用的英文名。

## 第三步：自查

- 每条 MVP 需求都有 AC；每条 AC 都能想象出一个自动化测试来验证它。
- 两个人分别读这份规格写测试和写代码，会不会写出不一致的东西？会的地方就是还要澄清的地方。
- screens.md 的每个页面都对应了 REQ，四种状态都写了（或标了 N/A 与理由）。
- 没有 TODO、TBD、待定。

用 forge_spec 提交。程序的 spec-lint 返回错误时，照着改，重新提交。
