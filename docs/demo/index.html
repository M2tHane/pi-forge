OVERVIEW

流程总览

一个需求从进来到交付，经过五段。每个实施阶段内部是同一个循环：多个 worker 并行写，审查员看代码并跑该任务自己的测试，再逐个合并；全量测试留到阶段末的门禁一次跑完。点任意方块看它具体做什么。

每个实施阶段内部（S0 … Sn）
合并冲突 → 退回给正在合并的 worker，自己解决后重新提交
ACT 1

需求变成规格

主会话先读需求原文，把模糊的地方一条条问清楚，再整理成带编号的需求（REQ）和验收标准（AC）。AC 只写用户能感知的行为，后面每一条都要有人认领、有测试覆盖。点需求卡片看详情。

ACT 2

架构师拆任务

硬依赖：等对方合入再开工软依赖：先对着契约写，合并前程序同步悬停看依赖 · 点卡片看详情

每条 AC 归谁

每格一条 AC，颜色是负责它的任务。每条 AC 必须恰好归一个任务，程序会检查。右上角带小圆点的是界面类、需要人工确认的 AC。点左侧需求名看详情。

ACT 3

并行施工

每条色带是一次 agent 运行（独立子进程）。按「播放」把整次构建压缩成几十秒回放：右边是程序记下的事件，上方圆点是此刻同时在干活的 agent 数。点色带看这次运行的细节。

ACT 4

每人交了什么

每个任务在自己的 git worktree 里干活，交付一组提交和一份交接笔记（做到哪、下一步、注意什么）。绿色是代码，蓝色是测试。


    

  


  

    
ACT 5
合并冲突：谁合并，谁解决

    

    

    
→
规则：worker 可以改任何代码文件，冲突留给后合并的那个人
计划里的改动范围只用来安排谁和谁同时干。真的撞上了，后合并的 worker 拿回自己的任务，在自己的工作区里解冲突、跑测试、重新提交。只有验收测试、规格这类它不能改的文件冲突，才交给用户。

交付
