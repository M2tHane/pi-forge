# 写验收测试

验收测试决定一个 task 能不能合并。它有两种失败方式，都要避免：

- **太松**：错误的实现也能通过（只检查状态码、断言过宽、什么都没测）。
- **太紧**：正确的实现也通不过（断言了规格没规定的东西、依赖实现细节、测试之间互相依赖）。
  这是 pi-flow 实测中返工的最大来源：先于实现写的测试写错了，没有办法自动发现。所以本技能大部分规则是防"太紧"的。

## 测试从哪里来

对每条 AC：

1. 把 Given 变成测试准备：通过接口创建需要的数据（团队、用户、数据源），不直接写数据库。
2. 把 When 变成一次调用：test_interface 中声明的 HTTP 接口、页面操作（无界面浏览器）或跨模块函数。
3. 把 Then 变成断言：状态码与错误码来自 openapi.yaml 与 errors/*.yaml；字段来自 schema。

测试名以 AC 编号开头：`[REQ-012.AC2] 同名数据源返回 409`。一条 AC 可以有多个测试（例如正常路径和边界情况），但都要标上编号。

## 只断言规格规定的东西

| 应该断言 | 不要断言 |
|---|---|
| 状态码、错误码 | 错误信息的文字（除非规格规定了） |
| AC 关心的字段及其值 | 整个响应的精确相等（契约追加字段就会失败） |
| 规格规定的排序、分页 | 规格没规定的顺序（用集合比较） |
| 字段类型与格式（uuid、时间格式） | 自动生成的具体 id、时间戳的值 |
| 副作用：通过另一个接口读回来验证 | 直接查数据库 |

规格没说清的地方：**不要猜着断言**。在 handoff 里列出来，这是规格需要补充的信号。

## 页面测试

- 只用无界面浏览器，只测 screens.md 里写明的交互和状态：新增后列表出现新项、空状态出现提示、无权限时按钮不存在。
- 选择器用可访问名称（role、label、文字），不用 CSS 类名或 DOM 结构，因为实现方式由 worker 决定。
- 视觉效果、布局、动画不测，交给 manual_checks。

## 独立与可重复

- 每个测试自己准备数据，用唯一的名字（加随机后缀），不依赖其他测试的执行顺序或残留数据。
- 公共的准备工作先用 tests/acceptance/_support/ 里已有的工具；需要新的辅助函数时，只能放在 tests/acceptance/_support/<本 task>/ 下，不改公共文件和别的 task 的目录。值得共享的写进 handoff，由 stage-qa 提出合并建议。
- 服务地址、端口、数据库都从环境变量取（PORT、FORGE_DB_NAME 等，S0 的公共工具已经封装），不要写死。
- 不 sleep 固定时长；需要等待时，轮询直到满足条件，并设置超时。

## 提交前

- 运行 `acceptance_list`，确认能被收集（没有语法或 import 错误）。
- 对照 AC 列表，确认每条都有测试。
- 读一遍断言：一个正确但写法不同的实现，能通过吗？一个漏掉 AC 的实现，会失败吗？
