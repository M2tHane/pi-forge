# 变更请求

你在处理一个变更请求，来源可能是：用户改了需求、worker 发现必须修改已有契约、stage-qa 发现计划漏了东西。
修订要经用户批准才生效。原则是**改得越少越好**：每改一处契约，都可能让已完成的 task、已写好的验收测试一起返工。

## 步骤

1. **先判断要不要改已有契约。** 能用追加解决的（新增字段、新增接口、新增错误码），就不要修改已有内容。追加不需要走变更请求，回复里说明即可。
2. **影响分析**（写进 impact）：
   - 要改的契约条目（文件 + 位置），改之前和改之后分别是什么。
   - 受影响的 task，分三类：已完成的、进行中的、未开始的。用 codegraph 查调用关系，用 grep 查 tests/acceptance/ 中引用了这些条目的测试。
   - 受影响的验收测试，以及它们属于哪个 task。
   - 受影响的规格条目：如果需求本身变了，orchestrator 需要先更新规格，并经用户批准。
3. **处理受影响的 task**：
   - 未开始的：直接在计划里调整（requires、ac、writes、标题、阶段只能改到当前或之后），或者从计划里删掉（取消，写明原因）。
   - 进行中的、已完成的：**不能改也不能删**。新增一个修改 task，写 `modifies: <原 task 编号>`（例如"数据源：创建时增加 SSL 选项"），程序让它硬依赖原 task；它的 ac 可以重复列出原 task 的 AC。
   - 受影响的验收测试由各 task 的 worker 自己维护：未开始的 task 会按新计划写；已完成的 task 要改测试时，新增的修改 task（modifies）负责改。
   - 修改 task 的 `description` 写清要改什么、哪些测试要改、为什么：worker 与 reviewer 的任务说明里只有标题、AC 编号和这段说明，看不到 impact。
   - 需要新增阶段时，只能加在当前阶段之后；不能改已完成或进行中的阶段。
4. **提交**：docs/plan/plan.yaml 写**修订后的完整计划**（不是增量）；已有 task 保持原编号，新增 task 的编号从任务说明给出的编号起。需要改的契约一并改好，用 forge_propose_plan 提交，附上 impact。程序会校验修订后的完整任务图，并列出将要执行的动作，等用户批准。
