### 1.1 A1 怎么实现

新增配置项 `implementation_gate.test_author`，默认 `true`。设为 `false` 时：

- **计划**：不派生 `.at` 任务。
- **范围**：impl 的 writes 自动加上 `tests/acceptance/<T>/**`。S0 已经有 `_support/**` 与 `S0-smoke/**`，不变。状态机"impl 不能改验收目录"那条规则对这个 task 放开。
- **任务说明**：说明里加一节："按 AC 编号为本任务写验收测试，放在 `tests/acceptance/<T>/`，用例标题带 `[REQ-xxx.ACn]`。"
  - 这一节写在用户消息里，不改 `agents/`、`rules/`、`skills/`。
  - 系统提示的稳定前缀不变，提示缓存不受影响。
- **预检**：不再等待 `awaitedAcctest`，因为没有 `.at`。`acceptance -- <T>` 照跑，跑的是 worker 自己写的测试。
- **覆盖率检查**：不变，仍然按 AC 编号做矩阵。
  - 唯一不同的是有缺口时的去向：不生成 `.at-n`（没有 test-author），改为给该 AC 所属的 impl 生成 `.fx-n`，标题写"补齐 AC 编号的验收测试"。
- **争议**：不会发生，因为测试是 worker 自己写的。
- **不变的部分**：审查、stage-qa、门禁、合并队列都不变。
- **记录**：记为偏离 81。单元测试覆盖计划派生、writes、状态机规则、覆盖缺口去向；加一条 e2e 跑通 A1 的一个阶段。

第二批要用的开关（A2 的 `stage_review: false`、A4 的合并判断）只在第二批触发时再做，第一批不准备。

## 3. 通过条件与决定规则

### 3.1 计分

- **隐藏测试（基础）**：40 个用例。"非法 JSON 返回 400"超出需求，不计分，所以满分 39。在交付后的 main 上跑。
- **隐藏测试（变更）**：6 个用例（`--change`），在变更交付后的 main 上跑。
- **回归**：新建后通过的基础用例里，变更后变成失败的个数。另外，项目自带测试在变更后的失败数单独列出，不进入判定。
- **agent 时间**：见第 5 节。新建与变更分开记，判定用两者之和。
- 每组 1 次，直接用这一次的结果。下面写的"平均"都指这一次的值。

### 3.2 第一批通过条件（A0）

1. **质量**：A0 的隐藏测试平均分（基础 + 变更）不低于 N 的平均分，并且 A0 每一次运行的回归都是 0。
2. **时间**：A0 的 agent 时间平均值不超过 N 的 3 倍。N 的 agent 时间按第 5 节计算。

| 质量 | 时间 | 结论 | 下一步 |
|---|---|---|---|
| 达标 | 达标 | M9 ① 通过 | 不跑第二批，进入 ②（Homebox）的方案 |
| 达标 | 超标 | 质量够但太慢 | 跑第二批 A2、A3，看能删掉什么 |
| 不达标 | 任意 | 不通过 | 停下来分析原因并汇报，不跑第二批 |

### 3.3 机制去留规则（A1、A2、A3 各自与 A0 比较；报告第 5 节，原文照录）

- 去掉某个机制后，**同时**满足以下三条，就从精简模式的默认流程里去掉这个机制（标准模式保留开关）：
  - 隐藏测试平均下降不到 1 个；
  - 回归不增加；
  - 它占 agent 时间的 10% 以上。
- 否则保留，并记录它的单位时间收益。
- "占 agent 时间" = （A0 的 agent 时间平均值 − 去掉它之后那一组的平均值）÷ A0 的平均值。`.at` 与 impl 并行，所以不按会话时长相加，而是用两组差值。
- **A4 触发条件**：A2、A3 各自都满足上面第一、二条（隐藏测试下降不到 1 个、回归不增加）。

## 4. 用户模拟脚本：每一种需要人回答的情况怎么回答

原则：脚本只做规则表里列出的动作。表里没有的情况一律算作"卡住"（见第 6 节），不即兴处理。每一次动作都写进 `interventions.jsonl`，记录时间、类别、触发时的状态和发出的命令。

| 情况 | 怎么识别 | 回答 | 计数类别 |
|---|---|---|---|
| P0 提问（`ask_user`） | RPC `extension_ui_request`（select/input） | select 选标签带"（推荐）"的选项，没有就选第一个；input 回"按你的推荐" | P0 问题数（按问题个数计） |
| P0 用文字提问（没有 `ask_user` 或它报告没有界面） | 主会话一轮结束，流程还在 P0，规格还没提交 | 回"都按你的推荐，继续" | P0 问题数（按轮计，另记这一轮里编号的问题数） |
| 规格审批、计划审批（P1）、阶段签收、交付确认 | `.forge` 状态为 awaiting_human / 等待批准 | `/forge approve`（交付时 select 选"确认合入并结束流程"） | 必经闸门（次数固定，单独列出） |
| P1 计划不是精简模式（A0/A1） | 计划里 `mode !== 'lean'` | 驳回一次，意见写"规模低于阈值，按精简模式重做计划"；第二次仍不是精简模式时，这次运行算流程失败 | 额外介入 |
| 测试争议转人工 | 任务停在等 `/forge-decide` | 同一个测试第一次选 `keep-test`；同一个测试第二次争议选 `fix-test`，说明写"按 worker 给出的依据改测试" | 额外介入 |
| task blocked（`forge_block` 提问） | task 状态为 blocked，并且有 blocked_reason | `/forge unblock <T> "按你的推荐做，以规格和契约为准"` | 额外介入 |
| task blocked（计数用完） | blocked，原因是失败次数用完 | `/forge unblock <T> --reset` | 额外介入 |
| 阶段 needs_human | stage_status = needs_human | `/forge accept <阶段> --note "模拟用户：按现状放行"` | 额外介入 |
| 超时复核（`forge_resolve_timeout` 等主会话决定） | 主会话收到超时通知 | 不处理，让主会话自己决定（它在主会话的工具里） | 不计 |
| N 组：原生 Pi 停下提问 | 最后一条消息以问句结尾，或含"请确认""是否需要"等 | 回"同意你给出的建议（默认方案），按建议继续。"，与 pi-flow 那次的原生对照一样 | P0 问题数（按轮计） |

- **上限**：
  - 同一个 task 被放行 3 次后又停住，算卡住。
  - 同一个阶段被放行 2 次后又进入 needs_human，算卡住。
- **报告的指标**：
  - **额外介入次数**：作为主要指标之一列出，每一类单独列一列。
  - **必经闸门次数**：只记录。
  - **P0 问题数**：单独列出。

## 5. 时间、成本与留档

### 5.1 agent 时间

- **pi-forge**：从发出 `/forge-build` 到交付完成的墙钟时间，减去等人的时间。
  - 等人的时间 = 流程处于 awaiting_human / needs_human 的时长（`--metrics` 已经这样计算），加上 task 处于 blocked 等人回答的时长（脚本从事件日志计算），加上 P0 中主会话等待回答的时长（脚本记录）。
  - 模拟脚本回答很快，但每 5 秒才轮询一次状态。这几秒算在"等人"里扣掉，不算 agent 的时间。
  - 新建与变更分开算，计算方法相同。
- **N**：从第一条消息发出到最后一轮结束的墙钟时间，减去脚本代答提问的间隔。
- **不扣除的时间**：模型限流引起的退避重试，算在 agent 时间里，两组一样。额度用完导致的整段停顿，按第 6 节处理。
- **核对**：脚本自己算出的值和 `/forge-status --metrics` 都写进结果。两者差别超过 2 分钟时，在报告里说明原因。

### 5.2 预估

| 组 | 耗时（新建 + 变更） | token（输入 + 缓存读，粗估） |
|---|---|---|
| N | 约 25–40 分钟 | 约 1–2M，全部是 GLM |
| A0 | 约 60–120 分钟 | 约 10–20M，其中 gpt 约 3–6M |
| A1 | 约 50–100 分钟 | 约 8–16M，其中 gpt 约 3–6M |
| **第一批合计** | **约 2.5–4.5 小时** | **约 20–40M** |

估算依据：
- pi-flow 在看板上，原生 1.1M、17.6 分钟；复跑三新建 75 分钟、9.8M，变更 62 分钟。
- GLM 比 gpt 慢，时间往上估。

花费按 magpie 的计价，用每次运行记录的 token 计算，报告里列出实际数字；事先不估美元。

另有两项准备开销，不计入上表：

- 冒烟：真实模型跑一次小项目，约 15 分钟、0.5 美元，不计入结果。
- 隐藏测试：在空项目上校准一次，确认分数为 0/39。

### 5.3 每次运行的留档

存放在 `~/pi-forge-runs/m9/<组>-<序号>-<时间>/`：

- 项目仓库，包括 `.forge/`，事件日志是 `.forge/events.jsonl`。
- 主会话与子进程的会话目录。
- `metrics-build.txt`、`metrics-change.txt`：`/forge-status --metrics --detail` 的输出，新建与变更各一份。

## 6. 中途出问题怎么办

### 6.1 卡住与超时

- **卡住**：同时满足下面三条，持续 30 分钟，算卡住。
  - `events.jsonl` 没有新事件；
  - 没有活跃的子进程会话在写输出；
  - 模拟脚本也没有可做的动作。
  - 对 N 组：会话 30 分钟没有新的 JSON 事件。
- **硬上限**：
  - N 组每次 90 分钟（约为上次原生 17.6 分钟的 5 倍）。
  - A0、A1 每次 4 小时（N 预估的 10 倍）。
- **处理**：卡住或超过上限时，停掉进程，用当时 main 上的代码计分。如果从未交付，就用集成分支 HEAD 计分。时间按上限计入。

### 6.2 失败分两类

| 类别 | 例子 | 是否计入该组结果 | 怎么处理 |
|---|---|---|---|
| 基础设施失败 | 额度用完造成的停顿超过 10 分钟；服务端持续 5xx；网络中断；电脑休眠；Pi 自身崩溃（栈不在 pi-forge 里） | 不计入，作废重跑 | 每组最多重跑 2 次；还失败就暂停这一批，向你汇报 |
| 流程失败 | 卡住、超过上限、放行次数达到上限、pi-forge 抛异常、第二次计划仍不是精简模式 | 计入，这次就是该组的结果，按实际结果计分 | 不重跑；如果是 pi-forge 的 bug，暂停这一批并汇报 |

- **修 bug 的规则**：如果要改 pi-forge 代码修 bug，这一批已经跑过的 A 组运行全部作废，用新的提交 SHA 重跑。N 组不受影响，不重跑。
- 改代码属于"修订"，要写进本文件末尾。
- 作废的运行保留留档，在报告里列出。

## 修订
