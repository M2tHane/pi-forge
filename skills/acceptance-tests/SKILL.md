# 写验收测试

本技能由 worker 使用：任务说明有『验收测试（由你编写）』一节，照本技能自己写 tests/acceptance/<T>/。reviewer 用同一份标准审查这些测试：每条 AC 有没有测试（程序已扫描编号）、是否真的走了 Given/When/Then 并且只经『允许的测试入口』、断言有没有被弱化、有没有依赖实现细节。缺失或形同虚设是阻塞问题。

测试和实现出自同一个人，最容易犯的错是**照着实现写断言**：期望值只能来自规格与契约，不能来自实现的当前输出。

**精简模式（lean）且 test_author 关闭**：全项目只有一份共享的集成测试，放在 tests/acceptance/suite/，辅助函数只在 suite/_helpers.js 一份（有就复用，缺什么往里补）。
写集成场景而不是逐条 AC 的用例：一个场景走完一条关键业务流程，测试名可带多个编号，如 `[REQ-001.AC1][REQ-001.AC2] 创建看板后列表可见`；本任务每条 AC 至少出现在一个场景的名字里。以下规则（只断言规格规定的、独立可重复）照样适用，但目录与辅助文件按这一段，不要建 tests/acceptance/<T>/ 或 _support/<T>/。

验收测试决定一个 task 能不能合并。它有两种失败方式，都要避免：

- **太松**：错误的实现也能通过（只检查状态码、断言过宽、什么都没测）。
- **太紧**：正确的实现也通不过（断言了规格没规定的东西、依赖实现细节、测试之间互相依赖）。
  这是 pi-flow 实测中返工的最大来源：测试写错了，没有办法自动发现。所以本技能大部分规则是防"太紧"的。

## 测试从哪里来

对每条 AC：

1. 把 Given 变成测试准备：通过接口创建需要的数据（团队、用户、数据源），不直接写数据库。
2. 把 When 变成一次调用：任务说明『允许的测试入口』一节列出的 HTTP 接口、页面操作（无界面浏览器）或跨模块函数。
3. 把 Then 变成断言：状态码与错误码来自 openapi.yaml 与 errors/*.yaml；字段来自 schema。

测试名以 AC 编号开头：`[REQ-012.AC2] 同名数据源返回 409`。
**优先写覆盖多条 AC 的集成场景**：一个场景走完一条用户路径，测试名带上它覆盖的全部 AC 编号（`[REQ-012.AC1][REQ-012.AC2] 创建后同名再建返回 409`），不要求每条 AC 单独一个测试；每条 AC 至少出现在一个测试名里。

**只测关键业务节点**：在『允许的测试入口』的公开边界验证行为。每条 AC 至少出现在一个测试名里，但不为每个边界情况各写一个；
优先主路径、权限、数据完整性、契约规定的错误码。测试越多，写错的机会越多，也越容易卡住正确的实现。

**入口要在本阶段可用**：Given 的准备和 Then 的观察，都只用『本阶段及之前已交付的接口』一节列出的接口，不调用后续阶段才交付的接口。需要后续接口才能准备或观察的场景，不自己想办法，写进 handoff。

## 只断言规格规定的东西

| 应该断言 | 不要断言 |
|---|---|
| 状态码、错误码 | 错误信息的文字（除非规格规定了） |
| AC 关心的字段及其值 | 整个响应的精确相等（契约追加字段就会失败） |
| 规格规定的排序、分页 | 规格没规定的顺序（用集合比较） |
| 字段类型与格式（uuid、时间格式） | 自动生成的具体 id、时间戳的值 |
| 副作用：通过另一个接口读回来验证 | 直接查数据库 |

规格没说清的地方：**不要猜着断言**。在 handoff 里列出来，这是规格需要补充的信号。

## 页面测试

- 只用无界面浏览器，只测 screens.md 里写明的交互和状态：新增后列表出现新项、空状态出现提示、无权限时按钮不存在。
- 选择器用可访问名称（role、label、文字），不用 CSS 类名或 DOM 结构，因为实现方式由 worker 决定。
- 视觉效果、布局、动画不测，交给 manual_checks。

## 独立与可重复

- 每个测试自己准备数据，用唯一的名字（加随机后缀），不依赖其他测试的执行顺序或残留数据。
- 公共的准备工作先用 tests/acceptance/_support/ 里已有的工具；需要新的辅助函数时，只能放在 tests/acceptance/_support/<本 task>/ 下，不改公共文件和别的 task 的目录。值得共享的写进 handoff，由 stage-qa 提出合并建议。
- 服务地址、端口、数据库都从环境变量取（PORT、FORGE_DB_NAME 等，S0 的公共工具已经封装），不要写死。
- 不 sleep 固定时长；需要等待时，轮询直到满足条件，并设置超时。

## 提交前

- 运行 `acceptance_list`，确认能被收集（没有语法或 import 错误）。它不证明断言正确。
- 新增或修改断言辅助函数时，用固定的正反例样本自检（不依赖实现）：符合契约的样本应通过，违反检查目标的样本应失败。
- 诊断标签与期望值用不同的具名参数（如 `{ label, expectedMessage }`）。规格没规定文案就不传 expectedMessage，不把标签当作期望值。
- 在执行 When 之前确认 Given 已成立：准备数据的请求也要检查结果（用户确实在项目里、角色确实建立）。
- 数据库行等带特殊原型的对象，按契约字段投影后比较值；对象原型不是业务条件。
- 返工时对照本轮全部失败和同一辅助函数的所有调用点，一次改完；修正夹具、参数误用、比较方式不算放宽。
- 对照 AC 列表，确认每条都有测试。
- 读一遍断言：一个正确但写法不同的实现，能通过吗？一个漏掉 AC 的实现，会失败吗？
